## 1. Where this round comes from

The October upgrade (DU1 to DU3.2, 29 and 30 September) shipped trust fixes, the operator's voice, the service-state layer and five new sources. On 30 September the owner looked at every surface and saw the changes only where the fleet deviated; the new breadth had reached the phone's Događanja list and almost nothing else. The reason was measured that night, not guessed (§2). The owner's verdict: the pass was good, the design and the experience stay, and the city must reach the screen. Four things were agreed:

1. Visible breadth on the wall and the phone: the rows the fitter deletes first become rows people see.
2. One departures line on the wall and the desktop: three departure rows become one row, freeing room for the city (about one row on the landscape walls, two on the portrait totem; the reveal scheduler brings the rest).
3. A reveal scheduler, not a marquee: an orchestrated, context-aware system decides what the wall shows and when, so the screen looks conventional and still gives "just when I thought I need that".
4. More city: what the system already holds and does not show, plus the few verified sources that remain.

## 2. What the evidence showed (30 September)

- **The wall's list holds five or six rows.** The box at 1920 by 1080 is about 500 px; a departure row is 64 px, a promise row (first, last, pharmacy) 86, a notice 102, an event up to 158. Three departures take 192 px. At 01:57 the wall showed two night departures, the "ZET javlja" row, the first tram and the pharmacy, and the box was full (`review.local/reveal/analysis/wall-now.png`).
- **The new kinds are deleted first.** `dropCandidate` (`app/src/kiosk/timeline.ts:236`) removes later-day rows, then the breadth kinds (rail, rain, cut, road, open), then the third departure, then events. That was the October plan's own rule (U3 §0.6), written to protect the departures contract.
- **The sources are thin where the places are.** HAK's five items are motorway junctions, never inside a 2 to 3 km circle around a tram stop. The 29 planned cuts were outskirts work (0 inside the Jelačić, Kvatrić, Črnomerec and Ljubljanica circles). Rain speaks only on wet steps. 45 of the City calendar's 60 items are all-day exhibitions, which `eventRows` skips. OpenStreetMap's 2,987 places with opening hours (1,212 inside the Jelačić circle: 220 shops, 164 cafés, 72 bakeries, 46 pharmacies) become at most one row, none while the pharmacy row is on, and that row is dropped first.
- **The phone showed the breadth the wall could not:** two City-calendar events in Sada, and Događanja with 266 events where a week earlier the whole city had 0 or 1 dated events a day.
- **The KPI measures the feed, not the screen.** The post-push night samples already read a median of 4.63 facts per place (baseline 0). Nothing measured what a screen showed. This pass adds that instrument (R4).
- **Held and not shown** (29 items in `review.local/reveal/analysis/withheld-facts.md`): the City's whole programme never reaches the wall map, the tonight panel or the paired Kultura; the hourly temperature is parsed and unused; tomorrow's forecast never becomes a sentence (a numeric DHMZ code); air, river, warnings and quakes never become a sentence; the `holiday` flag of the opening-hours lookup is hard-coded `false` (`app/src/kiosk.ts:514`, `app/src/city/feed.ts:202`), so on 1 November the wall would say the bakery is open. GTFS carries no accessibility fields and GTFS-RT no occupancy: nothing hidden there.
- **New sources** (`review.local/reveal/analysis/sources.md`): no new daily open source is left in Zagreb. Verified and chosen: DHMZ's radar composite, its biometeorological and heat/cold-wave XMLs, the public-holiday and school calendars, GPZ's street-level gas notices. Verified red or absent: Zagrebparking, Dinamo and Arena, City news, scooter GBFS, HŽ live delays, DHMZ UV for Zagreb, Čistoća, live Wikidata. HŽPP daily notices verified yellow and declined by the owner for this pass.

### 5.2 Seams built once (signatures verbatim; a package may add, never change)

**(a) Values and the static order (R0 creates `shared/kiosk/takt.ts`; R2 extends it):**

```ts
export type TaktKind = NearbyKind | 'departures' | 'next-departures';
export interface TaktCandidate { id: string; kind: TaktKind; atMs?: number; untilMs?: number; reserved: boolean; imminent: boolean; }
export interface TaktHistory { beat: number; shownAt: Readonly<Record<string, number>>; lastReveal: { kind: RevealKind; beat: number } | null; }
export const BASE_VALUE: Readonly<Record<TaktKind, number>>;
export function imminence(atMs: number | undefined, untilMs: number | undefined, now: number): number;
export function candidateValue(c: TaktCandidate, now: number, history: TaktHistory | null): number;
export const EMPTY_HISTORY: TaktHistory;
```

`candidateValue` = `BASE_VALUE[kind] × imminence × freshness` (freshness 1.2 when `history` is null or `shownAt[id]` is older than 10 min, else 1.0). R0 wires `byValue` (`timeline.ts`) to sort by `candidateValue` descending with reserved rows first, and `dropCandidate` to return the lowest-value non-reserved row; the later-day rule stays first.

**(b) The scheduler (R2 adds to the same file):**

```ts
export type RevealKind = 'advance' | 'page';
export interface TaktReveal { kind: RevealKind; ids: readonly string[]; replaces: readonly string[]; beat: number; }
export interface TaktOptions { capacity: number; rhythmMs: number; quiet: boolean; reduced: boolean; }
export interface TaktResult { page1: readonly string[]; reveal: TaktReveal | null; history: TaktHistory; }
export function beatIndex(now: number, rhythmMs: number): number;
export function takt(candidates: readonly TaktCandidate[], history: TaktHistory, now: number, options: TaktOptions): TaktResult;
```

`quiet` is true while a touch panel is open, in the paired phase, or while the service or outage fact pins the header; `takt` then returns page 1 and no reveal. `takt` is pure: the same inputs give the same result; it never reads the clock or the DOM.

**(c) The departures line (R1, `app/src/kiosk/timeline.ts`):**

```ts
export interface DeparturesLine { kind: 'departures'; id: 'departures'; cells: readonly NearbyRow[]; atMs: number; always: false; live: boolean; }
export type WallRow = NearbyRow | DeparturesLine;
export function groupDepartures(rows: readonly NearbyRow[]): WallRow[];
```

The leading run of `kind: 'departure'` rows becomes one `DeparturesLine` (1 to 3 cells, `atMs` of the first cell, `live` when any cell is live); other rows are unchanged. Markup: `li.nearby-row[data-kind="departures"][data-cells="N"][data-live]` holding `span.k-dep-cell[data-cell="1..3"][data-live][data-route]` with `.k-line-badge`, `time.nearby-when` and `.k-dep-headsign` (absent when the fitter removed it: `data-headsign="0"`). The fitter counts the line as one row and reserves it. `e2e/wall.ts` counts `departures` as the number of `[data-kind="departures"] [data-cell]`.

**(d) The next departures (R1 in `app/src/city/nearby.ts`, read by R2):**

```ts
export function nextDepartures(input: NearbyInput, shown: readonly NearbyRow[]): NearbyRow[];
```

The three departures after the shown ones, in `arrangeDepartures` order, `kind: 'departure'`, ids distinct from the shown; empty when fewer than four exist.

**(e) Holidays (R0 creates `shared/city/holidays.ts`; R3 adds the school calendar):**

```ts
export function easterSunday(year: number): { y: number; m: number; d: number };
export function isPublicHoliday(dayKey: string): boolean;   // 'YYYY-MM-DD', Zagreb day
export function isSchoolHoliday(dayKey: string): boolean;   // R3
```

**(f) New modules (R3), the wire contract in the U3 shape:**

| module | id | kind | at / until | geo | data |
|---|---|---|---|---|---|
| `dhmz-radar` | `dhmz-radar:<Last-Modified epoch s>` | `radar` (new `ItemKind`) | Last-Modified / +10 min | the Zagreb crop's bounds as a Polygon | `rainNear` (boolean), `rainCells` (count), `crop 'zagreb'`, `image '/api/radar/zagreb.png'` |

### 5.5 Efficiency rules

Two builders on one run, as in October: Claude orchestrates and executes the lanes in parallel worktrees; the owner's Codex session (astra) reviews and fixes each branch as its `done:` line lands, then owns the integrated tree for the deploy's gate (`integrated:` → `phase done`), then reads the observation (`pushed:`). Per lane: its own test subset once at the end, `npm run typecheck`, small commits, a report; then Codex's one review with local fixes committed on the branch. Per deploy: one integration, the gate once by Codex (the suite, the accept tier, the e2e wall spec), reds fixed by Codex without weakening a test, one whole-diff review by Codex, one 10-minute observation by Claude, push when green. No Claude reviewer agents; an item Codex cannot fix locally is a decision for the orchestrator, not a second review round; a second red on the same item is a follow-up unless it is a trust-core regression. Budgets: DR1 3.5 h, DR2 3 h, DR3 3 h from each wave's launch to its push; the orchestrator merges what is green when a budget expires. The protocol files: `review.local/reveal/run/prompts/CODEX-SESSION.md` (the Codex session), `CODEX-GATE.md` (the fallback launcher when no session runs).
